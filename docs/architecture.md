# 架构与数据含义

## 转发

`generate_exports.py` 直接解析本机 x64 PE 导出表，仅使用 Python 标准库，生成 `.def`、导出名表和 MASM 跳板。普通导出保存 Windows x64 参数寄存器 RCX/RDX/R8/R9、XMM0–3，解析真实入口后恢复寄存器，再尾跳真实函数，保持原调用者栈参数位置。

`D3D11CreateDevice` 和 `D3D11CreateDeviceAndSwapChain` 由 C++ 显式转发。真实 DLL 使用系统目录绝对路径加载；不在 DllMain 中加载运行库或安装观察器。成功返回的设备/上下文用于安装观察器；纯转发模式跳过安装。

## 观察

观察器给对象创建私有虚表副本，仅替换选定槽，不修改真实 D3D11 的代码段，也不更改全局只读虚表。保留调用真实方法的地址，采样后仍执行原调用。

旧实验中只复制公开 Device5 的 69 槽导致 `GetFeatureLevel` 访问私有第 69 槽时崩溃。因此本版本保留连续可执行地址组成的尾部，上限 512 槽，不能确定边界时拒绝安装。这是对已遇到问题的兼容处理，不是公开 COM 契约，不代表其他运行时布局普遍兼容。

观察模式将自身模块固定到进程生命周期，保留虚表副本，避免对象仍存活时 DLL 卸载导致悬空函数指针。当前不提供运行中卸载钩子。设备/上下文接口别名与更老版本不强行接管。

## 数据路径

```text
目标程序 → 代理设备创建入口 → System32/d3d11.dll
                              ↓ 成功返回 COM 对象
                       对象私有虚表副本
                       ├─ CreatePixel/ComputeShader → DXBC
                       └─ Draw / Dispatch
                            ├─ 无请求：轮询，继续真实调用
                            └─ 有请求：查询立即上下文绑定 → JSONL → 继续真实调用
```

记录的是实际调用前的状态，字段包括线程、上下文类型、调用参数、绑定 Shader（图形调用含 VS 及 GS/HS/DS）、资源地址、纹理尺寸/格式/采样数、缓冲大小与常量范围，图形调用另含 VS 资源、顶点/索引缓冲、DSV 与深度模板状态。

可选读回由 `constants=1` / `textures=1` / `buffers=1` 启用，对调试名称匹配 `filter=` 的调用执行：在原调用前于立即上下文拷贝到暂存资源并阻塞 `Map`，得到命令流中该位置的内容，代价是 GPU 同步卡顿。Buffer SRV 按视图 first/count 和 structured stride、raw DWORD 或 typed 格式换算字节范围。缓冲暂存资源默认 64 KiB，可用 `buffer_limit=` 提高到最大 4 MiB，按内容哈希去重；跨设备切换时重建暂存缓冲，唯一载荷每次采样最多 256 MiB。`constants=1` 还读取间接 Draw/Dispatch 的实际参数范围，解码 vertex/index count、instance count、start/base 等字段，正确保留负 base vertex。纹理每个资源每次采样只拷 mip 0 一次。暂存资源在采样结束时释放，未采样时不分配。

版本 5 对已观察的 DXGI factory 创建方法和交换链 Present/Present1 建立私有虚表观察；启动模式还用既有 Detours 事务截获系统 `CreateDXGIFactory/1/2` 导出，以覆盖设备外部创建的 factory。目录代理通过设备的 DXGI adapter parent 做尽力接入，并观察 D3D11CreateDeviceAndSwapChain 的返回交换链。接口别名、既有交换链和不经这些入口的创建仍可能漏采。

呈现入口递增进程内 `present_seq`，保留交换链身份，跳过 TEST 及同线程嵌套重复调用；不改变原方法参数或返回值。`frames=` 限制的是入口数，不承诺呈现成功或完整帧。首尾区间可不完整，多交换链必须另行关联，线程记录顺序也不是跨线程 GPU 执行顺序。`only_matching=1` 仅保存匹配 Shader 的调用，另受事件上限和帧请求 120 秒回调时间上限约束；无回调时不能保证及时完成。QPC 只表示 CPU 记录时间，不能衡量原游戏性能或 IK 的求解时间。

## 隔离与部署

可选启动接入使用独立 `inspector_hook.dll` 和 `startup_launcher.exe`。启动器仅调试其创建的 x64 进程：初始加载器断点后设置入口断点，在 EXE 入口恢复原字节和 RIP，暂停入口线程并分离调试器；随后以目标中对应模块的实际基址解析 `LoadLibraryW`，加载观察器并远程调用其显式初始化导出。初始化不在 DllMain 中执行。失败时只清理本次尚未恢复入口的子进程，成功后不提供在线卸载。

启动模式通过 Microsoft Detours 事务更新系统 D3D11 的两个设备创建入口；原型与原 API 一致，经跳板调用原函数后复用相同的观察器。钩子所在模块固定到进程生命周期，事务中登记现存线程，失败则中止事务。这里不包装/替换真实设备对象，不观察入口之前的设备，也不展开子进程。标准目录代理的导出表与转发实现继续独立构建和验证。

- 根目录可配置，每个进程按 PID 和创建时间隔离，避免多实例抢同一 `capture.request` 和 PID 重用覆盖文件。
- 请求临时文件写完后改名；重复待处理请求拒绝覆盖。采样完成必须检查结束记录。
- 安装拒绝覆盖已有 DLL，卸载核对安装文件 SHA-256；不随项目复制游戏 DLL、贴图、Shader 包、原始游戏采样或加载器补丁。
- 原实验目录与现有测试包保持不变。这里的 `src/` 源于旧代理源码，并清除了针对旧目录的路径、异常诊断处理器和游戏进程管理脚本。

## 适合回答的问题

- 哪些 PS / CS 在当前场景被使用？
- 某组后处理在什么尺寸的目标上运行？输入 SRV 与输出 RTV / UAV 如何衔接？
- 相邻降采样/模糊/合成调用是否使用同一份字节码？
- 配合字节码与调试名，哪些调用可能属于亮部提取、模糊和合成？

推断应附对应采样事件、Shader 文件和反汇编证据。没有纹理内容、常量值和帧边界时，不能直接宣称已经完整还原渲染算法。
